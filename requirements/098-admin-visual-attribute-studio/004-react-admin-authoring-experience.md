# 004 - React Admin Authoring Experience

**Status:** Definition authoring checkpoint implemented; visual mutations and Category-scoped release facade pending
**Depends on:** 001-003

## Objective

Add an Admin-only left-navigation destination and a complete React authoring
workspace at `/admin/attributes`.

The existing route proves API connectivity but is not the accepted production
experience. The replacement must make one Attribute's visual production flow
the primary task and relegate catalog metrics, release history and migration
debt to secondary views.

## Authoritative UX Reset

The implementation must follow 010 after its preview is accepted:

1. Use compact Category and dependent Field dropdowns; do not render a grid of
   every Category.
2. Keep a bounded, searchable option list in a narrow rail.
3. Open one option in a tabbed workspace: Definition, Visual production, Test,
   and History.
4. Keep the customer-facing visual preview and lifecycle/readiness actions in a
   persistent inspector.
5. Put `New attribute` at workspace level. Phase 1 requires an existing
   Category/Field and does not expose taxonomy creation.
6. Keep Generate, Upload, candidate comparison and Approve together in Visual
   production.
7. Keep option Save separate from Category Publish. Dirty, saved and approved
   option states must be unambiguous, while publication is available only from
   the owning Category release workflow.
8. Show duplicate legacy IDs only as scoped compatibility diagnostics. Unique
   options remain fully usable.
9. Use the shared theme-aware Select/Listbox for catalog navigation and filters;
   native operating-system popup colors are not an accepted theme contract.
10. Remove Category Publish from the authoring header and option inspector.
    Category publication, release history and rollback live in the separate
    Category Releases workspace defined by 010.

The route must never require an Admin to create a catalog-wide draft merely to
inspect an option or run a visual test. Draft/release implementation details may
remain catalog-wide on the server, but the UI presents an option-focused
editing workflow and a Category-level publication boundary.

## Navigation

- Preserve the existing role-gated `/admin` destination and Admin overview.
- Add `/admin/attributes` as a direct child destination using React Router;
  update `router.tsx` and route-registry matching together.
- Add Attributes to a shared Admin internal navigation/layout rather than
  creating a second top-level shell section.
- Admin sees edit controls; Support receives read-only presentation.
- Breadcrumbs show `Admin / Attributes / <field or option>`.

## Page Structure

### Catalog Rail

- compact Category and Field dropdowns with counts
- category and field are explicit navigation levels rather than a free-text
  filter or one flat option list; the option list is paginated within the
  selected field
- a deep link such as `?option=character.004` resolves the owning category and
  field on the server before rendering, even when that option is outside the
  first result page
- search by label, ID, alias and tag
- filters for mode, visual type, enabled state, lifecycle and validation
- badges for missing asset, invalid rule, unpublished change and retired item
- create option command according to permission; Category and Field creation is
  intentionally absent in Phase 1

`New attribute` opens the same workspace in create mode. Selecting an existing
Category/Field loads its layout and visual recipe defaults. Stable ID is shown
as system-generated and is returned only after Save. Admin authors the English
label; enabled locale labels are generated by the server-owned localization
workflow during Save.

### Editor Workspace

- identity: stable ID, revision and lifecycle
- localized labels/descriptions
- control type and ordering
- mode and character-type exposure
- prompt contribution and provider adaptations
- dependencies, conflicts, safety and Reference override rules
- visual generation/upload controls
- unsaved-state and concurrent-update warning

### Inspection Rail

- exact customer-facing visual card preview
- prompt impact, before/after and compilation order
- affected modes and saved-configuration usage count
- validation results grouped by error/warning/info
- release history and audit references

### Evaluation Workspace

- generated candidate grid
- fixed-fixture render comparison
- approve/reject with reviewer notes
- responsive preview for desktop and mobile controls

## Interaction Rules

- Enable/disable is explicit and confirms affected surfaces.
- Required dependencies are visible before publication.
- Destructive retirement uses a correctly layered AlertDialog.
- Save, publish, rollback and generation actions produce shared toast feedback.
- Forms use the global 0.75rem body font and theme radius/tokens.
- No nested decorative cards; use full-width work bands and framed tools.

## State and API

- TanStack Query keys include actor identity and catalog release/revision.
- Draft form state remains local to the route and warns before navigation loss.
- All APIs use `apiClient.ts` and Zod response schemas.
- Actor switching clears Admin draft and cached privileged data.
- Large images are URLs, never Base64 persistence.

The exact customer preview must render through the shared
`VisualOptionPicker`, `VisualImagePicker`, `VisualSwatchPicker` and
`VisualOptionGrid` component family. Admin code must not maintain a second card
implementation. The planned catalog metadata must eventually replace the
option-level maps and swatches in `visualOptionRegistry.ts`; do not copy those
tables into Admin UI.

## Accessibility and Responsive Behavior

- full keyboard editing and visible focus
- labeled icon buttons and tooltips
- status not communicated by color alone
- no clipped IDs, labels, generated variants or validation text
- desktop is optimized for dense authoring; mobile supports review and safe
  enable/disable but may defer complex rule graph editing

## Acceptance Criteria

- Admin can save and qualify individual Attribute changes, then publish the
  complete owning Category without editing files.
- Support cannot mutate catalog state.
- Customer preview matches the shared Visual Option component.
- Filters and selection survive refresh through URL parameters where useful.
- Legacy duplicate-ID debt reports its resolved count using the repository's
  single-brace i18n interpolation convention and makes clear that unique IDs
  remain editable.
- Desktop and mobile Playwright screenshots show no overlap or inaccessible
  controls.
