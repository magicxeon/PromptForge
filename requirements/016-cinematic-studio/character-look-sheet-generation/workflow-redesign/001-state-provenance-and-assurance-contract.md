# State, Provenance And Assurance Contract

**Requirement ID:** `016-CLWR-001`  
**Status:** Implemented; automated regression passed  
**Priority:** P0 foundation  
**Owning capability:** Character Profiles / reusable Character Looks

## 1. Problem

The current UI infers preparation state from `lifecycleStatus`,
`approvedVersionId` and the presence of generated assets, while source origin,
identity assurance, rights acknowledgement and optional validation are not one
explicit projection. This makes user-uploaded and system-generated sheets look
equally authoritative and encourages UI-only condition branches.

## 2. Canonical State Model

Persisted Look and Version lifecycle remains authoritative:

```text
Look: draft -> review -> approved -> retired
Version: source_ready -> review -> approved -> superseded/retired
```

The React workflow derives one presentation state without mutating lifecycle:

| Presentation state | Required persisted evidence | Primary action |
|---|---|---|
| `source_ready` | active Version and source data | Create Look Sheet |
| `generation_ready` | authorized Generation plan | Generate Look Sheet |
| `generation_active` | queued/processing Job pointer | View progress |
| `generation_completed` | completed owned result | Review this Look Sheet |
| `review_ready` | review media and crop manifest | Approve & use |
| `approved_unbound` | immutable approved Version | Use in this film |
| `approved_bound` | matching Cinematic assignment binding | Ready for Story Plan |
| `failed_recoverable` | terminal provider/adoption/bind error | Retry relevant operation |

`Source saved` is context. `Bind` remains a persisted system transition but is
not a separate step in the visible progress control.

## 3. Source Provenance

Extend the existing Version projection conservatively rather than replacing
`sourceMode`, `garmentAuthorities`, `approvedSheetAsset` or
`generationLineage`.

```ts
type CharacterLookProvenance = {
  kind: 'system_generated' | 'user_uploaded' | 'legacy_unknown';
  characterProfileId: string;
  characterProfileVersionId: string;
  sourceAssetIds: string[];
  generationResultId: string | null;
  generationJobId: string | null;
  recipeId: string | null;
  recipeVersion: number | null;
  recipeFingerprint: string | null;
  provider: string | null;
  model: string | null;
  recordedAt: string;
};
```

Rules:

- system-generated adoption stores the exact Character, Look, Version, recipe,
  Job/result, provider/model and authorized reference lineage already known by
  the server;
- user upload stores owned Asset IDs and the pinned Character version selected
  by the user, but association alone does not prove a visual match;
- no client may submit trusted owner IDs, provider lineage or validation status;
- no Base64 image is stored in the Look record;
- historical records that cannot prove origin use `legacy_unknown`.

## 4. Identity Assurance

Provenance and identity assurance are separate:

```ts
type CharacterLookIdentityAssurance = {
  status:
    | 'unverified'
    | 'user_confirmed'
    | 'lineage_bound'
    | 'validated'
    | 'validation_failed'
    | 'legacy_unknown';
  characterProfileVersionId: string;
  validationEvidenceId: string | null;
  updatedAt: string;
};
```

- `unverified`: uploaded media has not been checked or confirmed.
- `user_confirmed`: user accepted the mismatch warning and approved the upload.
- `lineage_bound`: media was generated by the canonical workflow using the
  pinned Character identity. This proves input lineage, not visual fidelity.
- `validated`: an optional qualified Character Match Check passed.
- `validation_failed`: the optional check did not pass; the creator may still
  continue after a warning, but no verified claim is shown.
- `legacy_unknown`: existing evidence cannot support a stronger status.

Never label `lineage_bound` as `validated`. Still-image validation also never
creates a `Video Character verified` claim.

## 5. Validation Evidence

Optional validation evidence is immutable and server-issued:

```ts
type CharacterMatchEvidence = {
  id: string;
  characterProfileId: string;
  characterProfileVersionId: string;
  characterLookId: string;
  characterLookVersionId: string;
  sheetAssetId: string;
  status: 'passed' | 'needs_review' | 'failed';
  checks: {
    characterPresent: boolean | null;
    singleCharacter: boolean | null;
    identityConsistency: 'pass' | 'review' | 'fail' | 'unknown';
    multiViewCoverage: 'pass' | 'review' | 'fail' | 'unknown';
  };
  provider: string;
  model: string;
  policyVersion: string;
  createdAt: string;
};
```

Raw provider reasoning and biometric embeddings must not be stored. Scores must
not be presented as legal identity verification. Evidence is private,
actor-authorized and retained with the Look audit contract.

## 6. Rights Declaration

The Sheet-specific declaration applies only to a user-uploaded complete Sheet:

```ts
type CharacterLookRightsDeclaration = {
  accepted: true;
  acceptedByUserId: string;
  acceptedAt: string;
  policyVersion: string;
};
```

The server derives actor and timestamp. AI-generated output does not request
this upload declaration. Existing generic Asset upload rights remain unchanged.

## 7. Downstream Projection

Story Plan, Storyboard and video preparation receive:

- approved Look and Version IDs;
- approved Sheet/view Asset authority;
- Character Profile and pinned Version IDs;
- source provenance kind;
- identity assurance status;
- optional validation evidence ID/status;
- existing crop manifest and Generation lineage.

Downstream consumers may show warnings but must not rewrite Look assurance. An
unverified Look remains usable by explicit creator choice; it cannot display a
verified Character badge.

## 8. Authorization And Error Contract

| Condition | Result |
|---|---|
| actor does not own/reuse Character or Look | `character_look_not_found` or existing authorization code |
| stale Look/Version | `character_look_source_not_ready` |
| result lineage does not match pinned context | `character_look_generation_context_mismatch` |
| validation evidence belongs to another actor/context | `character_match_evidence_invalid` |
| approved/bound Look discard attempted | `character_look_discard_not_allowed` |
| legacy record lacks assurance | project conservatively as `legacy_unknown` |

## 9. Implementation Steps

1. Add schema tests for provenance, assurance, rights and validation evidence.
2. Extend repository records with optional migration-compatible fields and
   conservative defaults; do not rewrite runtime JSON in routes.
3. Populate `system_generated` provenance during generated-result adoption.
4. Populate `user_uploaded` provenance and server-owned rights declaration
   during uploaded complete-Sheet review.
5. Add a single server projection helper used by Character Profile and
   Cinematic clients.
6. Extend Cinematic approved Look binding snapshot with assurance/provenance
   fields while preserving existing stable IDs.
7. Add actor, stale-version, tampered-lineage and legacy-read regressions.

## 10. Acceptance

- UI state can be derived from one server projection without inspecting raw
  provider payloads.
- System-generated and user-uploaded media are visibly distinguishable.
- Existing approved Looks continue to load with conservative assurance.
- Actor B cannot read or attach Actor A's evidence or media.
- No existing Generation/Credit/Asset record is duplicated or deleted.
- Database migration can map each nested contract to normalized records or JSON
  columns without changing public stable IDs.

## 11. Implementation Evidence (2026-09-01)

- `CharacterLookRepository` persists additive source/provenance/assurance/rights
  fields without rewriting legacy runtime records.
- `CharacterLookService` owns the normalized projection and media authorization.
- `CinematicApplicationService` binds the exact approved Version together with
  its provenance and assurance snapshot.
- Actor ownership, legacy projection, review rights, generated lineage and
  output-path confinement are covered by focused domain tests.
