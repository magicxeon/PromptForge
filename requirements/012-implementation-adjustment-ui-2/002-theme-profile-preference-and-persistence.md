# Theme Profile Preference And Persistence

**Parent:** `000-master-finalize-ux-ui-roadmap.md`

## 1. Current MVP

The current application has Mock Actor context but no durable authenticated User
Preference service. Store Theme Preference locally through the existing
actor-scoped persistence boundary and expose it through the global Footer.

Do not write directly to local storage from presentation components.

## 2. Future Profile Migration

Future profile DTO:

```text
UserPreferences
- schemaVersion
- themePreference
- colorModePreference?
- locale?
- updatedAt
```

Migration precedence:

```text
authenticated profile
-> actor-scoped local cache
-> default auto preference
```

The public Creator Profile must never expose private application preferences.

## 3. State Behavior

- Missing or corrupt values return `auto`.
- Unknown theme identifiers return `auto`.
- Changing Actor changes preference immediately.
- Route recommendation changes only when preference is `auto`.
- Explicit themes ignore route recommendation.
- Preference writes are synchronous locally and isolated by Actor ID.

## 4. Test Contract

- preference round trip;
- corrupt/unknown fallback;
- actor isolation;
- auto Fashion and Creative route resolution;
- explicit override;
- document `data-theme` and `color-scheme` application.

## 5. Software Design

```text
web/src/lib/theme/themeContract.ts
  identifiers, type guards and pure route resolution

web/src/lib/theme/themePreference.ts
  actor-scoped storage adapter

web/src/lib/theme/themeDocument.ts
  early bootstrap and document projection

web/src/lib/theme/ThemeContext.ts
  stable hook and context contract

web/src/lib/theme/ThemeProvider.tsx
  Actor + route orchestration

web/src/components/layout/FooterThemeSelector.tsx
  accessible global preference UI mounted by SiteFooter
```

`ThemeProvider` must be mounted inside `ActorProvider`. Presentation components
must call `useTheme()` rather than access local storage or mutate
`documentElement`.

## 6. Implementation Plan

1. Validate theme IDs at read and write boundaries.
2. Bootstrap the last active Actor theme before i18n and React rendering.
3. Rehydrate preference whenever Actor identity changes.
4. Sync route recommendation from `AppShell`.
5. Expose Footer theme options through an accessible radio group.
6. Add English and Thai Shell keys with interpolation parity.
7. Cover storage, route, document and menu behavior with focused tests.

## 7. Impact And Migration

- Local key is generated by the canonical actor-scoped persistence adapter.
- Actor switching never deletes another Actor's preference.
- A future authenticated preference API replaces the storage adapter behind the
  same typed contract; shared components do not change.
- Public Creator Profile DTOs remain unchanged.
