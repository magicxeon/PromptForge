# Phase 2-10 Durable Jobs and Batch Orchestration

**Status:** Local Groups, image Queue, JSON Video Tasks and Job Center exist; production worker durability pending (2026-09-07)

The current canonical entry point is Generation, with lifecycle orchestration
under `server/domain/generation/`, group persistence under
`server/repositories/generation/` and Fashion plan/run ownership under
`server/domain/fashion-blueprint/`. Commercial durability replaces the
process-local Queue adapter behind these contracts; it must not add a separate
Fashion queue or submit directly to providers.

`VideoProviderTaskService`/`VideoProviderTaskRepository` already retain local
video task state; do not discard that evidence or rebuild task tracking.
`GenerationJobCenterService` is the shared read/navigation projection, not an
execution queue. The current image Queue uses process memory; neither local
JSON task records nor UI polling prove transactional leases/outbox durability.

## 1. Business Requirement

Fashion packages may contain multiple paid operations and image jobs. Work must survive server restart, support pause/resume/retry and settle credits correctly per operation.

## 2. Domain Model

```text
GenerationPlan
  -> Batch
      -> Billable Operations
          -> Jobs
              -> Attempts
              -> Results/Events
```

Batch states:

```text
draft -> quoted -> confirmed -> queued -> processing
processing -> paused | partially_completed | completed | failed | cancelled
```

Job states:

```text
pending -> claimed -> running -> succeeded
                          -> retry_wait -> pending
                          -> failed | cancelled
```

These are target orchestration concepts. Map existing Group, Job, Fashion run
and Video Task enums explicitly instead of renaming their public responses.

## 3. Reliability

- Persist jobs before acknowledging submission.
- Use leases/heartbeats so abandoned running jobs can recover.
- Claim jobs atomically.
- Define maximum attempts and exponential backoff with jitter.
- Cancellation is cooperative and records whether provider cost already occurred.
- Successful jobs are never regenerated by resume.
- Provider request IDs and attempt metadata are retained for support.
- An ambiguous submit timeout is not proof that provider work failed. Reconcile
  the existing provider attempt before any newly billable retry; never blindly
  dispatch another paid request during migration or restart tests.

## 4. Billing Integration

- Confirmed Batch references reservation and immutable quote.
- Each operation settles or releases according to outcome policy.
- Infrastructure/provider failure is distinguished from user-requested regeneration.
- Safety rejection uses explicit refund/retry policy.
- Job worker uses CreditApplicationService through the owning transaction
  contract; it never writes balances or creates a second LedgerService.

## 5. Events and UX

- Persist authoritative events; SSE is a delivery mechanism, not the source of truth.
- Reconnecting clients use existing canonical status/Job Center tracking;
  polling remains valid. SSE is optional, not a prerequisite or second poller.
- Show overall and per-product progress.
- Pause stops new claims but does not corrupt running attempts.
- Retry failed only creates attempts for eligible failed operations.

## 6. Acceptance Criteria

- Restart during processing does not lose or duplicate accepted jobs.
- Pause/resume and retry failed only behave deterministically.
- Duplicate submission with same idempotency key returns the same Batch.
- Per-job credit settlement reconciles with Batch summary.
- Existing queue/provider behavior, including any supported progress/streaming,
  remains compatible; do not assume identical support across models.
- Concurrency, lease recovery and cancellation are covered by tests.
